# 1.9 Deploy Qdrant on GKE

## Goal

Qdrant running as a **StatefulSet** with persistent volume—vector store ready for Phase 2 ingestion.

## Scope

- `helm/qdrant/` or upstream Qdrant Helm chart with project values
- PVC via `volumeClaimTemplates`
- Internal ClusterIP service only (no public ingress in dev)

## Prerequisites

- [1.3 GKE](1.3-gke-cluster.md)
- [1.8 Helm](1.8-helm-charts.md) patterns established

## Implementation notes

```yaml
kind: StatefulSet
spec:
  volumeClaimTemplates:
    - metadata:
        name: qdrant-storage
      spec:
        accessModes: ["ReadWriteOnce"]
        storageClassName: standard-rwo
        resources:
          requests:
            storage: 10Gi
```

Use **StatefulSet**, not Deployment, for stable pod identity and per-replica PVC.

**Backups:** Full snapshot schedule is Phase [6.3](../phase-6-scaling-hardening/6.3-dr-backups.md); document PVC name here for later.

## Acceptance criteria

- [ ] Qdrant pod Running with bound PVC.
- [ ] `kubectl exec` or port-forward: Qdrant health/API responds.
- [ ] Restart pod: data persists on same PVC.
- [ ] Service DNS reachable from skeleton api pod namespace (network policy optional later).

## Validation commands

```bash
helm upgrade --install qdrant helm/qdrant -f helm/qdrant/values-dev.yaml -n platform
kubectl get pvc -n platform
kubectl port-forward svc/qdrant 6333:6333 -n platform
curl -sf http://localhost:6333/healthz || curl -sf http://localhost:6333/
```

## Rollback / cleanup

```bash
helm uninstall qdrant -n platform
# PVCs may remain by design—delete only if intentional data loss OK
```

## Production notes

- Size PVC for expected collection growth; monitor disk in Phase 4.
- Consider replica count / clustering only if justified—single replica OK for dev portfolio.
