# 3.2 Hybrid search + RRF

## Goal

Combine dense (Qdrant ANN) and sparse (BM25) retrieval with Reciprocal Rank Fusion.

## Scope

- Qdrant dense vector search + Qdrant sparse vector search
- BM25 sparse vectors generated with FastEmbed in application code for ingestion and query-time sparse retrieval
- Full chunk text stored in Qdrant payload for retrieval responses
- RRF merge → candidate list (e.g. top 50)

## Architecture decision

Use **Qdrant dense + Qdrant sparse** for hybrid retrieval, not a sidecar BM25 index.
Application code is responsible for generating BM25 sparse vectors with FastEmbed;
Qdrant stores and searches those sparse vectors but does not create them from text automatically.

The ingestion path must upsert both dense and sparse vectors for each chunk. Qdrant
payloads must include full chunk text in addition to existing metadata so the query
service can populate `RetrievedChunk.text` without a metadata DB lookup. Because the
current dev collection was created as dense-only and early 3.2 used a custom sparse
encoder, the 3.2 implementation requires dropping the dev collection followed by
re-ingesting dev data.
