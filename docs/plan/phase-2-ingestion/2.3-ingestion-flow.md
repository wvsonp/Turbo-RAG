# 2.3 Ingestion flow (parse → chunk → embed → upsert)

## Goal

End-to-end Prefect flow: read object from GCS (via Pub/Sub trigger) → parse → chunk → embed (Vertex `text-embedding-004`) → Qdrant upsert → PostgreSQL metadata in `rag_metadata`.

## Scope

### `services/workers/` (and/or Prefect flow package)

- Batched embedding calls to Vertex AI (`us-central1`, model `text-embedding-004` from config — not hardcoded in multiple files).
- Collection/schema conventions documented (collection name, vector size, payload fields).
- **Deterministic chunk / point IDs:** `point_id = uuid5(NAMESPACE_DOCUMENT, f"{document_id}:{chunk_index}")` (or equivalent stable scheme) so re-upserts target the same Qdrant point IDs.
- **Idempotency foundation for 2.5:** same `document_id` + chunk index → same point ID; metadata upserts use `document_id` as natural key where applicable.
- OpenAI API key (if used in dev tests only): read from `/var/secrets/openai-api-key` via Secret Manager CSI ([1.6](../phase-1-foundation/1.6-secret-manager.md)) — **not** `OPENAI_API_KEY` env var in Deployment manifests.

### Flow behavior

- Subscribe or poll `ingestion-uploads-sub` (from [2.1](2.1-gcs-pubsub.md)).
- Retry transient Vertex / Qdrant / Cloud SQL errors with exponential backoff.
- Document size limit for dev documented in flow config (e.g. 10-page PDF).

**Out of scope:** DLQ policy ([2.5](2.5-dlq-idempotency.md)); chunking strategy comparison ([2.4](2.4-chunking-mlflow.md)).

## Prerequisites

- [2.2](2.2-prefect-on-gke.md)
- Qdrant [1.9](../phase-1-foundation/1.9-qdrant.md)
- Cloud SQL [1.5](../phase-1-foundation/1.5-cloudsql.md) — `rag_metadata` database
- [2.1](2.1-gcs-pubsub.md) — workers SA has `aiplatform.user` and Pub/Sub subscriber

## Acceptance criteria

- [ ] Single PDF/text upload results in searchable vectors in Qdrant.
- [ ] Metadata row exists in `rag_metadata` for the document.
- [ ] Flow retries transient Vertex/Qdrant errors with backoff.
- [ ] End-to-end run completes in dev under documented size limit (e.g. 10-page PDF).
- [ ] Re-running the same upload / `document_id` yields the **same** Qdrant point IDs and does **not** increase point count (foundation for [2.5](2.5-dlq-idempotency.md) validation).

## Validation commands

```bash
# After upload trigger (see 2.1)
kubectl exec -n platform deploy/workers -- curl -sf \
  -X POST http://qdrant:6333/collections/<collection>/points/count \
  -H 'Content-Type: application/json' -d '{"exact":true}'

# Cloud SQL (via proxy or authorized pod)
# SELECT id, source_uri FROM documents LIMIT 5;

# Re-run flow for same object; count unchanged
curl -sf -X POST http://qdrant:6333/collections/<collection>/points/count \
  -H 'Content-Type: application/json' -d '{"exact":true}'
```

## Rollback / cleanup

- Disable flow deployment; drain subscription backlog before destroy.

## Production notes

- Enforce max object size and MIME allowlist at GCS upload boundary (ingestion API in later phase).
