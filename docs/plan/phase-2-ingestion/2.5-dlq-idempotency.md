# 2.5 DLQ + idempotency

## Goal

Failed Pub/Sub deliveries land in a dead-letter topic after bounded retries; re-running ingestion for the same document version does not duplicate Qdrant points or metadata rows; superseded versions have stale vectors removed. DLQ **topology** is built here (not in [2.1](2.1-gcs-pubsub.md)); **idempotent IDs and cleanup** are introduced in [2.3](2.3-ingestion-flow.md) and validated here.

## Scope

### Pub/Sub DLQ (Terraform in `infra/modules/pubsub/` or extension)

| Resource | Name (dev example) |
| -------- | ------------------ |
| DLQ topic | `ingestion-uploads-dlq` |
| DLQ subscription | `ingestion-uploads-dlq-sub` (for inspection / replay tooling) |

**Main subscription** (`ingestion-uploads-sub` from 2.1) — add:

```hcl
dead_letter_policy {
  dead_letter_topic     = google_pubsub_topic.ingestion_uploads_dlq.id
  max_delivery_attempts = 5
}
```

**Pub/Sub service agent IAM** (commonly missed; see [GCP Pub/Sub dead letter docs](https://cloud.google.com/pubsub/docs/dead-letter-topics)):

Let `pubsub_sa = "service-${data.google_project.project.number}@gcp-sa-pubsub.iam.gserviceaccount.com"`.

| Binding | Role | Resource |
| ------- | ---- | -------- |
| Forward failures to DLQ | `roles/pubsub.publisher` | DLQ topic `ingestion-uploads-dlq` |
| Redeliver / ack on primary sub | `roles/pubsub.subscriber` | Main subscription `ingestion-uploads-sub` |

Use `google_pubsub_topic_iam_member` and `google_pubsub_subscription_iam_member`.

### Dispatcher failure → DLQ path

When Prefect flow fails or dispatcher times out:

1. Dispatcher nacks message (does not ack).
2. Pub/Sub redelivers up to `max_delivery_attempts`.
3. After 5 failures, message forwarded to `ingestion-uploads-dlq`.
4. Dispatcher logs `document_version_id`, `pubsub_message_id`, failure reason.

### Idempotency validation

| Scenario | Expected outcome |
| -------- | ---------------- |
| Re-run same `(bucket, object_name, generation)` | Same Qdrant point IDs; point count for version unchanged; no duplicate `document_versions` row |
| Re-run after successful completion (duplicate Pub/Sub delivery) | Idempotent upsert; no extra points |
| Upload new generation of same `logical_uri` | Old version `superseded`; old Qdrant points deleted; `documents.latest_version_id` updated |
| Document shrinks (fewer chunks) | Orphan chunk rows and Qdrant points for indices ≥ new count removed |
| Forced failure (poison object) | After 5 delivery attempts, message on DLQ sub |

### DLQ replay (dev runbook)

Document in `docs/history/` on completion:

1. Inspect DLQ message: `gcloud pubsub subscriptions pull ingestion-uploads-dlq-sub --limit=1` (no ack until inspected).
2. Fix root cause (bad file, flow bug, quota).
3. Replay: republish message to main topic **or** manual Prefect run with same `{bucket, object_name, generation}`.
4. Replay must be idempotent — same `document_version_id` must not duplicate data.
5. Ack DLQ message after successful replay.

### Observability (required in dev)

- Structured log when message sent to DLQ (include `pubsub_message_id`, `document_version_id`).
- Metric or log line when DLQ subscription has undelivered messages > 0.
- Dispatcher exposes `/metrics` or logs: `ingestion_runs_total`, `ingestion_failures_total`, `dlq_forwards_total` (Prometheus format optional; log-based acceptable for dev).
- Full alerting deferred to Phase 4.

## Acceptance criteria

- [ ] `dead_letter_policy` present on `ingestion-uploads-sub` (`max_delivery_attempts = 5`).
- [ ] Pub/Sub service agent has publisher on DLQ topic and subscriber on main subscription.
- [ ] Forced failure (bad file / poison message) moves message to DLQ after 5 attempts.
- [ ] DLQ message visible on `ingestion-uploads-dlq-sub` (inspect without ack first).
- [ ] Re-run flow for same `(bucket, object_name, generation)` does not increase Qdrant point count.
- [ ] New generation supersedes old version; stale Qdrant points for old generation removed.
- [ ] DLQ replay runbook documented; replay is idempotent.
- [ ] Log or metric emitted when DLQ depth > 0.

## Validation commands

```bash
gcloud pubsub subscriptions describe ingestion-uploads-sub \
  --project=turbo-rag --format="yaml(deadLetterPolicy)"

gcloud pubsub topics get-iam-policy ingestion-uploads-dlq --project=turbo-rag

# Trigger poison message / bad file via upload + failing flow
# Wait for 5 redelivery attempts (check dispatcher logs)
gcloud pubsub subscriptions pull ingestion-uploads-dlq-sub \
  --project=turbo-rag --limit=1
# Inspect payload; ack only after recording message_id for replay test

# Idempotency: run flow twice for same document_version_id
kubectl exec -n platform deploy/workers -- curl -sf \
  -X POST http://qdrant:6333/collections/<collection>/points/count \
  -H 'Content-Type: application/json' -d '{"exact":true}'

# Stale cleanup: upload v2 of same object; verify v1 points gone
# SELECT document_version_id, status FROM document_versions WHERE logical_uri = '...';
```

## Rollback / cleanup

- Remove `dead_letter_policy` before deleting DLQ topic.
- Drain DLQ subscription before destroy.
- Scale dispatcher to 0 before subscription destroy.

## Production notes

- Monitor DLQ depth; alert on any DLQ message in prod.
- Define replay runbook and ownership before prod traffic.
- Cap `max_delivery_attempts` and ack deadline together so poison messages reach DLQ within SLA (e.g. < 1 hour).
