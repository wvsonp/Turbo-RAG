# 1.2 Terraform project layout

## Goal

Standard `infra/` layout with GCS remote backend, environment tfvars, and modules scaffold—so every later step adds resources through Terraform.

## Scope

- `infra/main.tf`, `variables.tf`, `outputs.tf`, `providers.tf`, `versions.tf`, `backend.tf`
- `infra/modules/` for gke, cloudsql, artifact_registry, pubsub, secret_manager, iam
- `infra/environments/dev.tfvars`, `prod.tfvars`

## Prerequisites

- [1.1 GCP bootstrap](1.1-gcp-bootstrap.md) complete (state bucket exists).

## Implementation notes

```
infra/
├── main.tf
├── variables.tf
├── outputs.tf
├── backend.tf
├── providers.tf
├── versions.tf
├── modules/
│   ├── gke/
│   ├── cloudsql/
│   ├── artifact_registry/
│   ├── pubsub/
│   ├── secret_manager/
│   └── iam/
└── environments/
    ├── dev.tfvars
    └── prod.tfvars
```

**State separation (prod-ready):**

```hcl
# dev:  prefix = "terraform/state/dev"
# prod: prefix = "terraform/state/prod"
```

Use distinct prefixes before first prod apply to avoid state collisions.

**Minimal CI checks (add in Phase 5; run locally now):**

```bash
cd infra && terraform fmt -check -recursive && terraform validate
```

## Acceptance criteria

- [ ] `terraform init` succeeds against GCS backend.
- [ ] `terraform validate` passes.
- [ ] `terraform plan -var-file=environments/dev.tfvars` runs without provider errors (resources may be pending).
- [ ] Module directories exist for all planned GCP services.
- [ ] `dev.tfvars` and `prod.tfvars` differ at least by `environment` and sizing variables.

## Validation commands

```bash
cd infra
terraform init
terraform validate
terraform plan -var-file=environments/dev.tfvars
```

## Rollback / cleanup

- `terraform state rm <address>` only when correcting mistaken imports—document in history.

## Production notes

- Pin provider versions in `versions.tf`.
- Consider Terraform Cloud or separate state buckets per environment for stricter blast-radius isolation.
